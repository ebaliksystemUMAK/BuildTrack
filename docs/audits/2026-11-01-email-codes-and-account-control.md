# Emailed codes, email check before approval, Super Admin account deletion, email only what is needed (2026-11-01)

Branch `feature/admin-phase4`, **not committed**. Three migrations, two new Edge Functions. Nothing was removed from any feature.

## What was wrong, and why

| Report | Real cause | Fix |
|---|---|---|
| "After submitting a registration it goes straight to the administrator, no OTP first" | The **Google** path. A Google account arrives already confirmed by Google, `complete_registration` then asked for nothing, so no email code was ever sent. (The email + password path already asked for a code.) | New `profiles.email_verified_at`. Only two things set it: typing the sign-up confirmation code (database trigger on `auth.users`), or typing a code BuildTrack emailed (service role `mark_email_verified`). The database now **refuses** `complete_registration`, an access request and an invitation code until it is set, so the screen cannot be bypassed. |
| "I chose OTP in Forgot password but I received the reset link" | The code and the link were the same Supabase email. Supabase decides what an email contains from the dashboard template, so a template without `{{ .Token }}` (or with the link) can never send "a code only", and the code option depended on a dashboard edit nobody could verify from the repository. | BuildTrack now makes, emails and checks its own 6-digit code (Edge Function `email-code`). The Supabase reset email is the link only. The two choices are independent: breaking one template can no longer break the code. |
| "Make sure email works, verify it" | Cron now runs every 5 minutes and the sender reaches Brevo, but **Brevo answers `401 Key not found` for all 42 attempts** (`email_log`). `.env.secrets` holds only the Brevo **SMTP** key (`xsmtpsib-...`); Edge Functions cannot use SMTP and the HTTP API needs an API key (`xkeysib-...`). | Owner action, see below. Everything on our side is built and tested; the new functions check the key first (`GET /v3/account`) and report a bad key plainly instead of silently sending nothing. |

## What was built

- **Email check before approval.** Migration `20261101210000_email_verification_and_codes`: `profiles.email_verified_at`, table `email_codes` (hash only, never the code), functions `issue_email_code`, `consume_email_code`, `mark_email_verified` (service role only), and the gates. Existing accounts that confirmed an email sign-up code are back-filled as verified; Google, instant-confirmed and admin-created accounts start unverified. Screens: Google registration now starts with "Confirm your email" (`components/EmailCodeStep.tsx`); the Basic user home shows the same card before access requests and invitation codes.
- **Emailed codes.** Edge Function `email-code` (verify_jwt on; signed-out visitors use the public key). Codes are HMAC-SHA256 of purpose + address + code with the service key, single use, 10 minutes, 5 tries, one per minute and 5 an hour **for every address** (an unknown address gets exactly the same answer and the same limits, so the form cannot be used to find out who has an account). A code is only emailed when the account exists and is active. Changing the password with a code signs the account out everywhere, writes `account.password_reset` to the audit log and emails a "password was changed" notice. The password rule is the same as the browser (`passwordProblem` is tested against `lib/passwordPolicy.ts`). The code never signs anyone in.
- **Email only what is needed.** Migration `20261101220000_email_only_needed_kinds`: a new category `inapp`. Bell only (never emailed): `pin.milestone`, `pin.resumed`, `report.submitted`, `report.reviewed`, `qa.defect_closed`, `project.archived`, `project.restored`, `project.manager_removed`, `attendance.concern_resolved`. Everything somebody has to act on or is waiting for stays emailed (QA requested / result / defect / item review, work assigned / returned / verified, access decisions, client reports and questions, reminders, announcements, account and security notices). A kind that is not classified is still emailed, and `pnpm test:communications` fails if the database creates a kind that nobody classified.
- **Super Admin deletes accounts.** Migration `20261101230000_account_deletion` and Edge Function `account-control` (Super Admin only). The database decides the outcome from the account's records (found from the catalog, so a table added later is covered automatically):
  - **no records anywhere** -> the sign-in and profile are removed completely (a snapshot is written to the audit log first and after);
  - **any record** (work, quality, reports, approvals, attendance...) -> the account is **closed**: name, email, phone, photos and ID files wiped, sign-in locked, sessions ended, permissions removed, and **every record stays exactly as it was**, shown as "Deleted account". Nothing a person did on site is deleted or re-attributed.
  - Never yourself, never a Super Admin, never twice. Severity tier 3: a written reason, the exact phrase `DELETE <email>`, **and a fresh authenticator code checked by the server** (`_shared/stepUp.ts`: Supabase MFA challenge + verify with the caller's own token; no secret is stored). The phrase and code are checked after every other rule, so a refusal never burns a code.
  - Screen: User management > open a person > **Delete account** (`pages/Admin/DeleteAccountModal.tsx`), which first shows what will happen and what is still attached (unfinished work, projects managed, teams).

## Confirmation tiers now in use

1. Plain confirm dialog: routine, reversible (enable, role change, whitelist removal).
2. Written reason + confirm: suspend, reject, reconsider.
3. Typed phrase: project recycle bin, record removal, permanent project deletion (`DELETE FOREVER <code>`), sheet deletion.
4. Reason + typed phrase + **fresh authenticator code**: account deletion (new). Permanent project deletion still relies on the aal2 session plus the typed phrase, the 30-day bin and the "no real records" rule; adding a fresh code there is a possible follow-up and is not done.

## Forgot password as step-by-step pop-ups (2026-11-02)

The screen is now: 1. email only ("Find my account") -> 2. pop-up with the two ways (link or 6-digit code) -> 3a. link: "Check your email" pop-up, or 3b. code: a pop-up that takes ONLY the code, checked by the server (`check_reset`, database function `check_email_code`, migration `20261102000000_email_code_check`, live `20261102012618`) -> 4. only after the code is accepted, the new-password pop-up (`verify_reset` checks the code again together with the password and uses it up). A wrong code stays on the code step; a code that expired during the password step sends the person back to ask for a new one. Step 1 never says whether the address has an account (that would reveal who is registered): it always continues, and an email is sent only to a real, active account. `email-code` redeployed (v4, JWT on); probes: malformed or wrong code and unknown address -> the same 400, bad address -> 400. Seen in the browser with a made-up address (nothing emailed): email step, choice pop-up, code pop-up, wrong code refused. Not seen: a real code arriving by email (needs the owner's mailbox after the Brevo key is set; the mail-key check already passes, so the new key is accepted).
