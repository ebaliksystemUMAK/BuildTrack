# Site controls: maintenance, feature isolation, forced logout

| Field | Value |
|---|---|
| File | `supabase/migrations/20261101150000_site_controls.sql` |
| Written | 2026-11-01 Manila |
| Status | **APPLIED** 2026-11-01 via the connector, live version `20261101052258`, verified (everything off, 7 feature rows, 33 guarded tables, privileges as designed, record counts unchanged) |
| Dependencies | `revoke_user_sessions` (existing), `audit_log`, `is_aal2()`, the work tables listed in the file |
| Reversible | Yes, switch everything off first; rollback block at the end of the file |

Everything starts OFF. Applying the file changes nothing for any user until a Super Admin turns something on in Admin > Site controls. It adds tables, functions and one column, and one statement trigger (`zz_site_guard`) on about 33 work tables.

| Object | What it is |
|---|---|
| `site_controls` (one row, id = 1) | Maintenance switch, message, optional expected return time. Read only through functions. |
| `feature_locks` | Seven named features (`quality`, `daily_reports`, `blueprint_editor`, `client_reports`, `site_issues`, `site_visits`, `attendance`): locked flag, non-admin roles affected, message. |
| `site_write_block(feature)`, `site_guard()` | Decide whether the caller's write is refused. Admins, Super Admins and service-role callers (devices, jobs, Edge Functions) are never refused. No row or an error means allow. Refusal code is `BT503`. |
| `zz_site_guard` triggers | Statement-level, before insert / update / delete, on the guarded tables. Core tables (pins, timeline, pin photos, checklist items, blueprints and revisions, projects, members, blueprint access) are paused by maintenance only; a feature lock never touches them. |
| `get_site_status()` | Anyone, including the login page: whether maintenance is on, the message, and for a signed-in person whether they are restricted and which features are paused for them. |
| `get_site_controls()`, `set_maintenance`, `set_feature_lock` | Super Admin with the authenticator only; audited (`maintenance.*`, `feature.*`). |
| `force_logout_targets`, `preview_force_logout`, `force_logout` | Super Admin with the authenticator only. Active non-admin accounts in the chosen roles (and project). Needs the count from a fresh preview, the exact phrase `LOG OUT <count>` and a reason; one run per 10 minutes; audited (`user.force_logout`). |
| `profiles.force_logout_at` | Time of the last forced logout of that account; the app signs the person out when it is later than their sign-in. |

Not changed: Auth settings, token lifetime, any existing policy, function or table data, the biometric Edge Functions.

## Verification queries (read-only, after running)
```sql
select maintenance_on, message, returns_at from public.site_controls;                       -- expected: false, '', null
select feature, locked from public.feature_locks order by 1;                                -- expected: 7 rows, all false
select count(*) as guarded_tables from information_schema.triggers where trigger_schema = 'public' and trigger_name = 'zz_site_guard' and event_manipulation = 'INSERT';
select p.proname, has_function_privilege('anon', p.oid, 'execute') as anon, has_function_privilege('authenticated', p.oid, 'execute') as authenticated
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace where n.nspname = 'public'
   and p.proname in ('get_site_status','get_site_controls','set_maintenance','set_feature_lock','preview_force_logout','force_logout') order by 1;
select has_table_privilege('authenticated', 'public.site_controls', 'select') as controls_readable, has_table_privilege('authenticated', 'public.feature_locks', 'select') as locks_readable;
select count(*) as profiles_with_force_logout from public.profiles where force_logout_at is not null;   -- expected: 0
```
Expected: `anon` true only for `get_site_status`; `authenticated` true for all six; both table checks false.

## Trying it without disturbing real users
Sign in as the Super Admin and turn maintenance on **with a message that says it is a test**, check the banner, then switch it off within a minute. Real non-admin users are paused for that minute; if that matters, pick a quiet hour. Feature isolation is safer to try: pause one feature for the role "Basic users" only, which affects nobody in practice. Do not run a forced logout as a test on real accounts.

## If you are locked out (switch everything off from the SQL editor)
Admins and Super Admins are never refused, so this is only for a Super Admin who cannot reach the page (for example, no authenticator).
```sql
update public.site_controls set maintenance_on = false where id = 1;
update public.feature_locks set locked = false;
```
