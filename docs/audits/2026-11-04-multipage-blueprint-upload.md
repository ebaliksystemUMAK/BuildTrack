# Multi-page PDF blueprint uploads

The existing upload dialog now reads the PDF page count and expands into a scrollable grid of page cards. New plans have a separate required label and optional level/area per page, selection controls, an on-demand preview, a selected/saved count and fixed upload actions. Each selected page becomes a blueprint in the chosen project/type. Existing plan revisions select one source page and retain the plan's identity, earlier revisions, mapped work and QA history. Images keep the single-plan flow and the 25 MB limit.

The form keeps one PDF worker open for page counting and rendering; it processes uploads sequentially to bound canvas memory. Replacing a file or unmounting invalidates old work, releases the worker and revokes preview URLs. Preview images are bounded to 900 pixels and saved plan previews to 3200 pixels. The original PDF remains private with each page's plan, following the existing per-plan storage layout; a multi-page import therefore keeps an original copy per selected plan.

Each page gets a stable revision UUID. Retry skips saved pages, reuses the blueprint already created for a failed page, and checks the revision UUID before writing. A failed response after a committed insert is confirmed through the existing read policy before any file cleanup. If confirmation is unavailable, files stay in place for the next retry. Only a confirmed failed attempt removes its unused uploads. New upload controls retain project/type selection and notes after partial progress, and do not relabel an already-created sheet during retry.

No schema, storage-policy or role-permission change is needed. The existing blueprint/revision/storage policies and guards remain authoritative. No live project or file was created during tests.

Focused tests exercise the real form handlers and upload helper with local substitutes for PDF rendering, private storage and PostgREST: all-page labels, validation, selected-page order, image/revision compatibility, page preview cleanup, late-file cancellation, partial retry, original-file retention, and committed/uncertain-save idempotency. A real two-page PDF is also parsed and rendered through the production helper with PDF.js's Node-compatible build and its optional native canvas; page counts, selected-page pixels, preview bounds and cleanup pass. The check is in `pnpm check`. Full application checks, TypeScript, 740 SQL cases, production build and the 5,000-pin load test passed. Real-browser visual verification remains unperformed.
